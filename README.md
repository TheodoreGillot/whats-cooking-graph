# What's Cooking? A graph analysis of recipes and ingredients

Graph-analytics project. We model recipes as a graph of ingredients (two ingredients
are linked when they are cooked together) in order to:

1. **analyse the ingredient graph**: structure, connectivity, central ingredients, and
   whether its communities match the world's cuisines;
2. **recommend recipes**: given the ingredients a user has, rank existing recipes with a
   personalised PageRank on the recipe–ingredient graph, compared with two baselines.

**Status:** data cleaning, the ingredient-graph analysis (`src/run_all.py`), the recommender
and its evaluation (`notebooks/04_recommender.ipynb`), the Streamlit demo (`app.py`) and the web
app (`server.py` + `web/`) are in place.

## Cleaning

### Food.com (`src/clean_foodcom.py`)

Rules:

1. `tags`, `steps` and `ingredients` are stored as text of Python lists; they are parsed with
   `ast.literal_eval`.
2. Ingredient names are mapped to canonical names with `ingr_map.pkl` (column `replaced`),
   after repairing its corrupted names (`CANONICAL_FIXES`, table below).
3. A merge raw name → canonical name is kept only if the two share a word (punctuation and
   plurals ignored) and every word of the canonical name appears in some raw name; otherwise
   the raw name is kept. This rejects wrong merges such as "blanched slivered almonds" → "liver"
   or "boneless beef rump roast" → "rum". Exceptions checked by hand:
   - `ACCEPTED`: correct merges with no shared word (green onions → scallion, achiote → annatto,
     chilies → chili, brand names → artificial sweetener / cooking spray);
   - `KEEP_RAW`: names that must stay separate (green onion dip, dried green onion flakes);
   - `OVERRIDES`: names redirected by hand (slivered almonds, cranberry juice, ravioli).
4. `minutes` ≤ 0 or > 1 day are set to missing (the maximum was 2,147,483,647).
5. A `cuisines` column lists the What's Cooking cuisines found in the tags
   (english → british, caribbean → jamaican, cajun / creole → cajun_creole,
   southern-united-states → southern_us).
6. `n_reviews` and `mean_rating` use rated reviews only (rating > 0; rating 0 means a review
   without a rating).

Bugs found in `ingr_map.pkl` and repaired:

| Corrupted name | Correct name | Cause |
|---|---|---|
| flmy, cornflmy | flour, cornflour | "our" replaced by "my" |
| fetum, pastum, polentum | feta, pasta, polenta | final -a read as a Latin plural |
| tamarus, havartus | tamari, havarti | final -i read as a Latin plural |
| olife | olive | olives → olife (like knives → knife) |
| chily | chili | chilies → chily (like berries → berry) |
| couscou | couscous | final s removed |
| cre mushroom, ature … | cremini mushroom, … | "mini" cut out of words |

Expected output:

```
merges rejected (raw name kept): 175
ingredient names: raw 14942 -> clean 11296
missing minutes: 3094
recipes with a cuisine: 39024
recipes with >= 5 rated reviews: 50978
saved 231637 recipes
```

The authors' map reduces the names to about 8,000; we keep 11,296 because rejected merges keep
their raw name. This is deliberate: two names for one ingredient are less harmful than one
wrong name.

### What's Cooking: alignment with Food.com names (`src/clean_whatscooking.py`)

What's Cooking writes the same ingredient in many ways ("eggs" / "large eggs", "green onions" /
"scallions"), which splits one ingredient into several graph nodes. Each name is mapped onto
the Food.com canonical names, with these rules tried in order:

1. a name checked by hand (`SAME_AS`, e.g. tumeric → turmeric, jalapeno chilies → jalapeno);
2. a raw Food.com name → its canonical name (the cleaned map above);
3. already a Food.com canonical name → unchanged;
4. preparation words removed (`MODIFIERS`: large, chopped, fresh, minced, grated, …), then 1–3 again;
5. otherwise the name is kept (it exists only in What's Cooking).

"ground" is deliberately not a modifier: ground cumin ≠ cumin, ground beef ≠ beef.

Expected output:

```
ingredient uses matched: exact 84.9% -> with rules 94.2%
distinct names: 6702 -> 6188
```

(6,702 rather than 6,714 because names differing only by case are already merged by
`normalize()`.) `prepare_data.py` reads the aligned file, so the whole analysis uses these names.

Effect on the ingredient graph:

| | raw names (`train.json`) | aligned names |
|---|---|---|
| nodes | 1,691 | 1,520 |
| edges | 16,766 | 14,700 |
| largest component | 1,470 | 1,368 |

Limitation: Food.com itself keeps "garlic" and "garlic clove" apart, so they remain two nodes.

## Graph analysis (`src/run_all.py`)

### Graph model

- **Bipartite graph** recipes ↔ ingredients (`build_bipartite`): the raw model.
- **Ingredient graph** (`build_ingredient_graph`), a filtered one-mode projection:
  - nodes: ingredients used in ≥ 20 recipes (`MIN_RECIPES`); isolated ones are kept;
  - edges: pairs that co-occur in ≥ 10 recipes (`MIN_COOC`) **and** have
    NPMI > 0.10 (`MIN_NPMI`), where
    NPMI(a, b) = log[p(a, b) / (p(a) p(b))] / (−log p(a, b)) ∈ [−1, 1];
  - **undirected** (co-occurrence is symmetric) and **simple** (repeated co-occurrences become
    the `count` attribute, not parallel edges);
  - edge attributes: `count`, `npmi` (strength of the association), `distance = 1 − npmi`
    (used as a length, so strong associations make short paths).

NPMI is used instead of raw counts because counts measure popularity, not affinity: without the
filter, salt is linked to almost every ingredient.

### Conventions

- Diameter, radius and average path length are computed **on the largest connected component,
  in hops** (unweighted), because isolated ingredients make distances infinite.
- Communities are computed on the largest connected component.
- "Home cuisine" of an ingredient = the cuisine with the highest lift P(cuisine | ingredient) /
  P(cuisine), which corrects for the very unbalanced cuisine sizes. "Diversity" = normalised
  entropy of the lift profile (0 = one cuisine, 1 = all cuisines).

### Scripts and outputs

| Script | Computes | Writes |
|---|---|---|
| `clean_whatscooking.py` | name alignment (see above) | `data/processed/whats_cooking_canonical.json` |
| `prepare_data.py` | bipartite and ingredient graphs | `data/processed/recipes.json`, `bipartite.pkl`, `ingredient_graph.pkl` |
| `structure.py` | size, density, degrees, components, diameter, radius, average path, clustering | `results/structure.json`, `figures/degree_distribution.png` |
| `centrality.py` | degree, strength, betweenness (unweighted and with `distance`), closeness, eigenvector, PageRank; Spearman correlations | `results/top10.csv`, `spearman.csv`, `centrality.json`, `figures/betweenness_vs_diversity.png` |
| `communities.py` | Louvain (weight `npmi`), label propagation, raw-count baseline, NMI with home cuisine, shuffled-label baseline, degree-preserving null model, robustness to seeds and resolution | `results/communities.json`, `community_profiles.csv` |
| `sensitivity.py` | the same graph for 27 combinations of the three thresholds | `results/sensitivity.csv` |

### Expected results

- 1,520 nodes, 14,700 edges, density 0.0127; 153 components: one of 1,368 ingredients (90%)
  and 152 isolated ingredients.
- Largest component: diameter 5, radius 3, average shortest path 2.80; average clustering 0.47.
- Top ingredient by degree: soy sauce; betweenness: sugar; closeness: ground cumin;
  eigenvector: ginger. Spearman(betweenness, cuisine diversity) = 0.30.
- Louvain: 5 communities, modularity 0.531 (raw-count graph: 0.194, with 5 communities plus
  46 isolated ingredients counted as their own community).
- NMI between communities and home cuisines: 0.326, against 0.013 on average (maximum 0.020)
  for 200 shuffles of the labels.
- Unweighted modularity 0.479, against 0.152 for a random graph with the same degrees
  (degree-preserving rewiring).
- Agreement between Louvain runs with different seeds: NMI 0.76–0.89. Label propagation
  collapses into 2 communities (one floods most of the graph), so the analysis relies on Louvain.

## Recommender (`src/recommend.py`, `notebooks/04_recommender.ipynb`)

### Method

- **Catalogue:** Food.com recipes with at least 5 rated reviews (50,978 recipes, 6,580
  ingredients, 450,958 recipe–ingredient edges).
- The recipe–ingredient bipartite graph is stored as a sparse incidence matrix B
  (recipes × ingredients), so a query takes milliseconds.
- **Personalised PageRank (`score_ppr`):** a random walk starts on the user's ingredients, goes
  to a recipe that uses one of them, then to one of that recipe's ingredients, and so on; at
  each step it returns to the user's ingredients with probability `restart`. A recipe's score
  is the share of time the walk spends on it. The implementation is checked against
  `nx.pagerank` (alpha = 1 − restart) on 2,000 recipes: maximum difference 1.5e-12.
- **Baselines:** `score_overlap` (number of the user's ingredients in the recipe) and
  `score_tfidf` (cosine similarity, rare ingredients weighted by IDF).

`python src/recommend.py` runs the check against NetworkX and prints the three rankings for
one example basket.

### Evaluation protocol

- Task: take a real recipe with ≥ 6 ingredients, give the method a random half of them, and
  find the rank of the original recipe. Metrics: hit@1, hit@10, MRR, median rank. Ties count
  as the average position.
- 500 validation recipes to choose `restart`, 1,000 different test recipes for the results
  (seed 42). All methods receive identical queries.
- Paired bootstrap (1,000 resamples) for 95% intervals of the differences.
- "Noisy fridge" variant: the query also contains 2, 4 or 6 ingredients the recipe does not
  use, drawn with probability proportional to their frequency.

### Expected results

`restart` chosen on validation: 0.99. MRR rises from 0.592 at 0.1 to 0.759 at 0.9–0.99, and
short walks also win in the noisy-fridge variant: PageRank then behaves like an ingredient
overlap where each ingredient is weighted by 1 / (number of recipes using it).

Test set, clean basket:

| | hit@1 | hit@10 | MRR |
|---|---|---|---|
| overlap | 0.652 | 0.904 | 0.766 |
| tf-idf | 0.609 | 0.866 | 0.697 |
| personalised PageRank | 0.694 | 0.879 | 0.762 |

95% intervals of PageRank − baseline:

| | hit@1 | hit@10 | MRR |
|---|---|---|---|
| vs overlap | [0.031, 0.054] | [−0.036, −0.016] | [−0.011, 0.002] |
| vs tf-idf | [0.055, 0.114] | [−0.008, 0.033] | [0.044, 0.086] |

MRR on the test set when the fridge also holds unrelated ingredients
(`figures/recommender_noise.png`):

| extra ingredients | overlap | tf-idf | PageRank |
|---|---|---|---|
| 0 | 0.766 | 0.697 | 0.762 |
| 2 | 0.597 | 0.637 | 0.587 |
| 4 | 0.463 | 0.581 | 0.443 |
| 6 | 0.337 | 0.528 | 0.377 |

In short: personalised PageRank puts the right recipe first more often than both baselines
when the basket matches what the user wants to cook; TF-IDF is the most robust when the basket
also contains unrelated ingredients, because PageRank's 1 / degree weighting lets one rare,
unrelated ingredient dominate. With a clean basket the target recipe contains every query
ingredient by construction, which favours the overlap baseline.

The last cell of the notebook builds the ingredient graph of the catalogue (same thresholds)
and its Louvain communities: 1,547 nodes, 12,265 edges, 7 communities, modularity 0.5. The
communities read as cuisine families (baking, soups and stews, Mediterranean, East Asian,
American barbecue, Mexican, drinks), although Food.com has almost no cuisine labels.

## Demo app (`app.py`)

```bash
streamlit run app.py
```

Pick the ingredients you have; three tabs:

- **Cook now:** recommended recipes with the share of ingredients you have, cooking time,
  rating, what you have and what is missing, and the steps. "Different meals" keeps one recipe
  per cuisine family (community of the Food.com ingredient graph).
- **What to buy:** the ingredients the random walk reaches most often from your basket.
- **Ingredient map:** an interactive graph (pyvis) of your ingredients and their strongest NPMI
  neighbours, coloured by community.

The sidebar switches between PageRank and the two baselines, and sets the restart probability.
The app reads `results/foodcom_ingredient_graph.graphml`, written by the last cell of
notebook 04.

## Web app (`server.py`, `web/`)

A designed version of the demo: a small FastAPI server around `src/recommend.py` and the
ingredient graph, and a single page (plain HTML, CSS and JavaScript, no build step).

```bash
python src/fetch_images.py    # once, optional: ingredient photos
python server.py              # then open http://127.0.0.1:8000
```

Five views share the fridge on the left:

- **Cook:** recipes ranked by the chosen method (graph walk, TF-IDF or overlap, switchable in the
  top bar), with photos of what you have and what is missing, time, rating and the method.
  "One dish per cuisine family" keeps one recipe per community.
- **Plan:** search a dish or a recipe. Suggestions appear as you type and only show what the
  catalogue has: dish names (1- to 3-word phrases found in at least 3 recipe names, with their
  number of recipes) and the most reviewed matching recipes. A dish shows its usual ingredients
  (share of the recipes using each), what is already in the fridge and a shopping list to copy,
  then the versions that contain at least half of its usual ingredients, sorted by how many
  ingredients would have to be bought. A recipe shows its exact shopping list and its method.
  A short hand-checked list (`SAME_INGREDIENT` in `server.py`) treats Food.com variants such as
  garlic / garlic clove or ground beef / lean ground beef as the same item here.
- **Shop:** ingredients to buy next, ranked by how many of your 30 best-matching recipes use them.
- **Map:** the ingredient graph, either around your fridge (your ingredients and their strongest
  NPMI partners) or whole (all 1,340 connected ingredients, ForceAtlas2 layout, each ingredient
  keeping its three strongest links). The legend names the communities and isolates one on click;
  clicking an ingredient lists its best partners with their NPMI.
- **Invent:** a graph-guided new dish. Starting from your ingredients, the graph adds one at a time
  the ingredient with the highest mean NPMI with everything already chosen, then reports the
  closest existing recipe (Jaccard similarity). If the `ANTHROPIC_API_KEY` environment variable is
  set, Claude (`claude-sonnet-5-5`, change it with `CHEF_MODEL`) writes the method for exactly
  these ingredients; the language model never chooses ingredients. Without a key, everything else
  works.

The map layout is computed once and cached in `results/foodcom_layout.json`. Cytoscape.js and the
fonts (Young Serif, Figtree; SIL Open Font License) are stored in `web/`, so the app works offline.
Ingredient photos come from [TheMealDB](https://www.themealdb.com), free for educational use; they
are downloaded locally into `data/images/` and not committed.
